Inspected contract from `examples/yolov5`: input is 640x640, 3-channel RGB, planar CHW uint8; the source image is aspect-fit resized and black-padded. On the user's board, VIP 2.0.3.2 reports input sizes `[640,640,3,1]`, format 2 (`UINT8`). This is the runtime's reverse-dimension representation corresponding to the demo's NCHW byte layout. The example postprocessor assumes three COCO heads in order output[0]=stride 8 (80x80x3x85), output[1]=stride 16 (40x40x3x85), output[2]=stride 32 (20x20x3x85), anchors from COCO YOLOv5, and person class index 0. Actual output metadata has not yet been printed by the board run. The example's vector end pointer uses `size-1` as an exclusive end and omits each head's final value. Its fixed 0.4 threshold also excludes low-confidence boxes needed by ByteTrack. The CPU decoder validates expected element count and does not copy tensors; the adapter now accepts direct or reverse VIP dimension order for the three expected output shapes.

The public wrapper header declares `awnn_init`, `awnn_uninit`, `awnn_set_input_buffers`, `awnn_run` and `awnn_destroy` as `void`; `awnn_create` returns a nullable context and output access returns pointers. Its implementation ignores many VIP query/map/flush return values and logs-and-continues for run/cache errors, so callers cannot recover those statuses through the current ABI. `awnn_create` must be checked for null. VIP metadata APIs are `vip_query_network`, `vip_query_input` and `vip_query_output`, which return VIP status values.
